# afrog 文档重构 PRD

## 1. 背景

当前 `afrog` 的文档入口分散在 `README`、`docs/`、`afrog.wiki` 和官网仓库中，存在以下问题：

- 缺少唯一权威入口，用户不清楚该优先阅读哪一份文档。
- 内容按时间自然堆积，未按用户角色和使用场景分层。
- 教程、参考、机制说明、FAQ 混放，检索成本高。
- 中文和英文没有统一的结构策略，后续双语维护成本高。
- 官网仓库尚未承载完整文档站角色，专业感不足。

本项目希望通过一次信息架构重构，建立一套可长期维护、兼容中英文双语、适合官网展示的文档体系。

## 2. 目标

### 2.1 产品目标

建立一套面向官网的文档体系，使 `afrog` 文档具备如下特征：

- 结构清晰，用户可以快速定位所需信息。
- 文档入口统一，官网成为唯一权威阅读入口。
- 内容按角色分层，兼顾初学者、PoC 作者和 SDK 用户。
- 中文优先落地，英文可在同一结构下平滑补齐。
- 文档可持续维护，并能跟随代码演进稳定更新。

### 2.2 成功标准

- 新用户 5 分钟内完成第一次扫描。
- PoC 作者 15 分钟内写出第一条可运行 PoC。
- SDK 用户 20 分钟内完成最小集成。
- 核心功能在 3 次点击内可到达。
- 中文与英文目录结构完全一致。

## 3. 非目标

本阶段不追求以下内容：

- 一次性重写所有历史文章。
- 在第一版就补齐全量英文正文。
- 在 Wiki 中继续扩展新的权威说明文档。
- 先做大规模视觉改版再整理信息架构。

## 4. 目标用户

### 4.1 使用者

关注安装、首次扫描、参数、配置、输出、性能和排障。

### 4.2 PoC 作者

关注 PoC 结构、表达式、提取器、内置函数、`requires`、`brute`、OOB、调试和最佳实践。

### 4.3 开发者 / 集成方

关注 SDK、同步异步执行、回调与流、输出结构、配置项和内存控制。

### 4.4 贡献者

关注 PoC 提交规范、文档贡献规范、命名和评审要求。

## 5. 核心原则

1. 官网文档站是唯一权威入口。
2. `afrog` 主仓库是文档内容真源。
3. `README` 只承担产品门面职责，不承载完整手册。
4. 教程、How-to、Reference、Explanation 必须分层。
5. 中文优先，但必须从一开始就兼容英文镜像结构。
6. 新功能合并前至少补齐中文文档；英文至少保留同路径占位页。

## 6. 载体职责划分

### 6.1 `afrog` 主仓库

职责：

- 维护文档正文。
- 与代码变更一起评审文档改动。
- 作为官网文档的数据真源。

### 6.2 `afrog-website`

职责：

- 负责站点渲染、导航、搜索、国际化切换和 SEO。
- 不承载独立的“另一套正文”。

### 6.3 `afrog.wiki`

职责：

- 仅保留历史文章归档。
- 迁移完成后，在旧页面顶部增加“已迁移到 Docs”的说明或跳转。

### 6.4 `README.md`

职责：

- 项目介绍。
- 安装方式。
- 三个最高频命令示例。
- 文档站入口。

## 8. 内容分层规范

### 8.1 Tutorial

用于“带用户做成一件事”，强调步骤感和成功路径。

### 8.2 How-to

用于“告诉用户如何完成一个任务”，强调任务导向。

### 8.3 Reference

用于“精确定义参数、字段、返回结构”，强调完整性和准确性。

### 8.4 Explanation

用于解释机制设计、原理和边界。

## 9. 双语策略

### 9.1 目录策略

- 中文路径：`docs/zh/...`
- 英文路径：`docs/en/...`
- 两套目录必须保持一一对应。

### 9.2 URL 策略

- 所有 slug 使用英文。
- 中文与英文共享同一套 slug 逻辑，避免未来外链和 SEO 结构漂移。

### 9.3 编写策略

- 中文版先写完整内容。
- 英文版同步创建同路径文件。
- 英文未完成时允许先保留摘要或占位说明，但不能缺失路径。

### 9.4 页面元信息

建议每篇文档统一包含以下 frontmatter：

```yaml
title:
slug:
lang:
summary:
status:
source:
last_reviewed:
```

其中 `status` 建议支持：

- `stable`
- `draft`
- `migrating`
- `deprecated`

## 10. 首批上线范围

第一期优先完成以下 10 篇中文核心文档：

1. `docs/zh/index.md`
2. `docs/zh/getting-started/install.md`
3. `docs/zh/getting-started/first-scan.md`
4. `docs/zh/reference/cli-options.md`
5. `docs/zh/user-guide/configuration.md`
6. `docs/zh/user-guide/output-and-report.md`
7. `docs/zh/poc/quickstart.md`
8. `docs/zh/poc/syntax.md`
9. `docs/zh/poc/helper-functions.md`
10. `docs/zh/sdk/quickstart.md`

这批内容能够先建立官网专业感，并覆盖最常见的三类用户路径。

## 11. 实施阶段

### Phase 1：定骨架

- 确定目录、slug、导航和双语规则。
- 建立 PRD、迁移清单和写作规范。
- 精简根 `README` 的职责定义。

### Phase 2：迁核心

- 输出首批 10 篇中文核心文档。
- 建立英文镜像目录和占位文件。
- 为旧文档增加迁移状态标记。

### Phase 3：收入口

- 官网切换到新结构。
- Wiki 改为归档与跳转。
- 清理重复内容和失效入口。

### Phase 4：持续演进

- 补齐英文版正文。
- 建立 Release Notes、贡献指南和文档 CI 规则。
- 形成“功能变更必须附带文档更新”的维护流程。

## 12. 验收标准

- 官网文档首页能明确分发到使用者、PoC 作者、SDK 用户、贡献者四条路径。
- 中文目录结构完整可导航。
- 首批核心文档全部可读且链接闭环。
- Wiki 中的核心入口已被替换为新文档站链接。
- README 不再重复大段说明性内容。

## 13. 风险与控制

### 13.1 风险：迁移周期内出现新旧入口并存

控制方式：

- 在旧文档顶部标记状态。
- 迁移后优先补跳转说明。

### 13.2 风险：英文版长期缺位

控制方式：

- 强制建立英文同路径文件。
- 在 CI 中对缺失镜像页给出 warning。

### 13.3 风险：教程继续充当参考手册

控制方式：

- 以目录分层约束内容类型。
- Review 时检查是否把参数定义混进教程页。
